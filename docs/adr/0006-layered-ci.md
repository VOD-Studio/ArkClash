# 0006 分层 CI，单一必需检查，发版只构建一次

- 状态：已采纳（2026-11-07）

## 背景

第一版 CI 的问题都在 v0.1.1 发版前后暴露出来：

- 签名这条路只在发版时才第一次跑，结果在正式发版时失败（macOS 的 tar 往签名包里带了 `._` 文件）。
- `ci.yml` 和 `release.yml` 的 HAP 任务几乎逐行重复；合并发版 PR 时，同一个提交编了 2 次内核、3 次 HAP；发版的未签名包和签名包是两次不同的构建。
- 只改文档也跑完整构建；`main` 上连续合并会取消前一个提交的验证。
- Geo 数据每次下载上游最新版，同一个提交不同时间构建出的 HAP 不一样。
- 只能证明"能编译"：没有提交信息、workflow 安全、依赖漏洞、产物内容的检查，CI 红了也能合并（当时是私有仓库，免费套餐没有合并规则）。

## 决定

1. **按阶段分层**：PR 预检（快速检查 → 内核 → HAP）、合并后（同样的检查，不取消，签名并保留测试包）、发版、每周维护。
2. **单一必需检查**：所有任务汇总到「CI 通过」，合并规则只要求它。按条件跳过的任务算通过，所以可以放心按变更范围跳过构建。
3. **可复用的构建单元**：`core.yml`、`hap.yml` 被 CI、发版、每周任务共用。
4. **签名每次都跑**：有签名材料时，同一次构建同时产出未签名包和签名包。
5. **发版只构建一次**：release 模式加调试证书，两个包内容一致；不用缓存，构建任务只读，只有发布任务能写；附来源证明。
6. **机器人 PR 用 `workflow_dispatch` 触发 CI**：不为发版 PR 和 Geo 数据 PR 维护个人 token。
7. **数据依赖锁定并镜像**：`geodata.lock` 加本仓库的 `geodata` 预发布，每周由机器人开 PR 更新。
8. **仓库公开**：换来合并规则、不限 Actions 分钟、CodeQL、secret 推送拦截和来源证明。私有的只有存放华为 Command Line Tools 的仓库。

## 被否决的方案

- **按 workflow 级 `paths` 过滤**：被过滤掉的 workflow 不会产生检查结果，必需检查会一直等待。改为在任务里判断，再由汇总任务统一给结果。
- **发版 PR 用个人 token（PAT）**：要人工创建、会过期，泄露后能写仓库。
- **按上游提交 SHA 锁定 Geo 数据**：上游 `release` 分支每天强推成一个孤立提交，旧 SHA 迟早不可达。
- **zizmor 建议的 `$/...` 本地引用写法**：actionlint 不认，GitHub 文档仍是 `./...`，暂时关掉这条审计。

## 后果

- 只改文档的 PR 约 1 分钟出结果；有缓存时完整 PR 约 3 分钟。
- 外部 fork 的 PR 只跑检查和内核，HAP 在合并后由 `main` 补跑。
- dependabot 的 PR 要在 Dependabot secrets 里另配一份工具链 token。
- 依赖漏洞扫描暂不计入必需检查：首次扫描发现内核调用到约 20 个已知漏洞，修复后改为必需。
- 下一步要补的是测试：把内核的纯逻辑从 cgo 代码里拆出来跑 Go 单元测试，ArkTS 本地单元测试，以及接真机的自托管 runner（只在 `main` 和定时任务上跑，不能给外部 PR 用）。
