# 0009 ArkClash 自有命令挂在 controller 上

- 状态：已采纳（2026-11-07）
- 扩展：[0003 UI 通过 external-controller 和文件通道与内核通信](0003-ui-core-via-external-controller.md)

## 背景

0003 留下一个缺口：ArkClash 自己的命令（按 `applyOverrides` 重载配置、带宽测试等）没法通过 mihomo 的 API 下发。配置管理（#35）又定了连接期间订阅的下载和写盘由 VPN 进程负责，界面要能把手动更新、添加订阅交给它，并拿到结果。

调研（#23，分支 `research/vpn-command-channel`）比较过的其他方案都不可用：

- `filesDir` 文件监听：官方没有说明扩展进程在后台能不能收到事件，也没有回传结果的途径。
- 公共事件：应用在后台时不投递动态订阅的事件，VPN 扩展进程一直在后台。
- rpc 和共享内存：要先 connect，`VpnExtensionAbility` 不支持。
- 重复调用 `startVpnExtensionAbility` 并带 Want：参数只在首次启动时有效。

## 决定

**通道**

- core 包的 `init()` 里用 mihomo 的 `route.Register`，在 external-controller 上挂一组 `/arkclash/` 路由，和 mihomo 的 API 共用 `127.0.0.1:19090` 以及每次连接随机生成的 secret。注册必须早于第一次 `hub.ApplyConfig`。
- 同样在 `init()` 里调 `route.SetEmbedMode(true)`，关掉 `PUT`/`PATCH /configs`、`POST /configs/geo`、`/restart`、`/upgrade` 和规则开关这几个接口。界面改出站模式和局域网代理，改用 `PATCH /arkclash/configs`，这个接口只接受这两项。

**谁执行**

- 内核自己能完成的命令（重载、带宽测试、模式和局域网代理、运行状态查询）由 Go 直接处理。
- 订阅类命令（添加、更新、列表变更）由 Go 通过 NAPI 线程安全函数转给 VPN 进程的 ArkTS，处理完再把结果交回 Go 响应。
- 订阅更新逻辑只写一份 ArkTS，两个进程共用，包括下载、内容检查、摘要、状态文件和失败退避。未连接时在界面进程里运行，连接中在 VPN 进程里运行。两者只在注入的下载器上不同：
  - 界面进程直连下载。
  - VPN 进程先调 `core.fetch`，由 Go 用 mihomo 的 `component/http` 经内核按规则发出；失败再直连。VPN 进程开了 `protectProcessNet`，ArkTS 发出的请求本来就是直连。订阅到期、节点全挂时，只有直连能拿到续费后的订阅。
  - 这一条修订了 #35 的「连接中经代理端口下载」，下载不再依赖配置有没有开代理端口。

**连接中的订阅操作全部交给 VPN 进程**

- 手动更新；「全部更新」由界面对每个订阅分别发一次请求。
- 添加订阅：VPN 进程下载、检查，写好 YAML、摘要和状态文件后，把名称和用量返回给界面，界面再写入列表文件。界面在返回前被杀会留下孤立文件，应用在未连接时启动就清理掉。
- 修改链接：用新链接更新，成功后界面才保存新链接。
- 本地配置始终由界面写，VPN 进程不碰。

**结果回传**

- 界面发起的命令同步返回结果。请求方中途断开，VPN 进程照样把已经收到的更新做完，结果写进状态文件。
- VPN 进程自己发起的变化（自动更新成功或失败、随后的热切换）通过 `GET /arkclash/events` WebSocket 推送。页面可见时订阅，不可见时退订，回到页面时重新读文件。

**写入方交接**（#35 定了同一时刻只有一个写入方）

- 界面开始连接后，不再发起新的更新，进行中的照常完成。
- VPN 进程的 `onDestroy` 先取消定时器和进行中的下载，再停内核。界面确认已断开后，再恢复前台调度。
- 交接的瞬间两边可能同时写同一个订阅的文件。写文件一律先写临时文件再改名，所以每次写入都是完整的，最后写的那份生效，不加跨进程锁。
- 界面认为正在连接、却连不上 controller 时，先重新探测；确认已断开就由界面自己执行，其他错误直接报给用户。

## 后果

- 不新增端口和通道，0003「controller + 文件通道」的格局不变。本机其他应用没有 secret，同样调不了 `/arkclash/`。
- 新增了 Go → ArkTS 方向的调用。从 Go 的线程调用线程安全函数需要真机验证；走不通就改成 ArkTS 常驻一个异步任务，等 Go 下发命令（长轮询），代价是一直占着一个 libuv 工作线程。
- VPN 进程会加载 YAML 库和更新逻辑，摘要放在 TaskPool 里计算。自动更新的定时器跑在 VPN 进程的 ArkTS 里，长时间待机后能不能按时触发，需要真机观察。
- 界面进程只在未连接时下载订阅，而且只直连。代理端口只剩出口 IP 这类功能还在用。
- 开启 embed 模式后，以后要在应用里更新 Geo 数据、开关单条规则，都得自己写接口。
- 共享的更新逻辑要放在两个进程都能依赖的那一层（`shared/` 或新建一层）。实现时同步更新 `docs/architecture.md` 的分层表和 `scripts/check-arch.py`。
