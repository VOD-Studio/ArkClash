# 0013 用系统进程事实恢复异常终止的运行宿主

- 状态：已采纳；宿主回归与 API 26 真机启停、代理转发已通过。

## 背景

VPN 进程被系统直接杀死或设备重启时，不会执行 `onDestroy`，也不会补写 `runtime-stopped.json`。仅凭旧 `runtime-instance.json` 保持 `unknown`，会使界面永远无法恢复离线写入；停止操作也会反复等待死进程不可能生成的回执。反过来，controller 不可达可能只是暂时失联，不能据此认定宿主停止。

本机 API 26 SDK 的 `appManager.getRunningProcessInformation()` 明确返回当前应用的运行进程；自 API 11 起查询自身应用不需要 `GET_RUNNING_INFO`。`@kit.ArkTS` 的 `process.pid` 标识调用方。进程记录没有 VPN 类型，不能依赖猜测的系统进程名或把某个历史 PID 当作永久实例身份。

## 决定

- 保留宿主 `running / stopped / unknown` 三态。controller 的带凭据运行快照证明 `running`；同一 secret、同一扩展实例的清理回执，或系统确认当前应用仅剩调用方 UI 进程，证明 `stopped`。其余情况保持 `unknown`，禁止业务写入。
- 进程查询只由 UI 进程使用。必须成功返回且包含调用方 PID；空列表、缺少调用方、查询异常、存在任何其他本应用进程，均不能作为停止证据。其他进程不按名称筛选，宁可继续保留未知，也不将新宿主或复用 PID 误判为停止。
- 查询前后核对 `runtime.json` 与 `runtime-instance.json`。查询期间改变会话或实例，丢弃旧证据。死亡恢复不删除、覆盖实例或伪造清理回执，重启前的残留也按同一规则处理。
- `CoreClient` 在模块内持有正在启动的 Promise 和宿主操作代次。从准备启动设置起，到系统启动调用和就绪等待结束，所有宿主查询保持未知，覆盖写好 runtime 但 VPN 进程尚未创建的窗口。已进入的离线短提交仍先完成，后续业务消费者由未知状态禁写。
- 公开停止入口取消启动代次，先请求系统停止，再等待该启动 Promise 收尾，最后重新核停止证据。启动自身的取消和超时清理调用私有资源停止函数，不等待自身 Promise。HTTP 就绪请求返回后再次核取消代次，迟到成功不得发布。
- HTTP 运行查询前后同时核 secret 和扩展实例，拒绝跨实例的迟到快照。原有 boot/revision 顺序检查、清理回执实例隔离和 VPN 生命周期资源释放规则继续保留。
- 未知宿主不会伪造用户的 `started` 意图。首次恢复仍以未启动外观呈现，并明确显示“代理状态未确认”和“停止并确认代理”的动作；该动作始终可用，活宿主失联时也能请求停止。只有已确认的资源或真实启动意图驱动暂停外观。
- 不增加后台轮询、心跳、租约、原生桥或额外系统权限。恢复发生在已有前台状态查询及启停边界；启动就绪和停止确认沿用原有有界等待。

## 后果

- 异常死亡或设备重启留下的文件可以安全恢复，旧文件仍可供判断实例隔离，不再阻塞下一次连接。
- 正常清理可凭回执确认资源已释放，即使系统尚未回收空闲扩展进程；回执必须仍属于当前运行设置和当前实例。
- 本应用未来增加其他进程时，保守规则可能使离线资格保持未知；届时应另行定义可靠进程身份，不能放宽成忽略未知进程。
- 本记录补充 [0012](0012-profile-state-and-runtime-separation.md) 的宿主三态取证，不改变 [0003](0003-ui-core-via-external-controller.md) 的业务通信通道。

## 验证

- `make test TESTS='runtime dashboard profiles proxies'`：86 项通过，覆盖旧残留、存活但失联、回执隔离、凭据和实例换代、缺失实例标记、启动停止竞态及迟到 HTTP 响应。
- HBP-AL00、OpenHarmony-7.0.0.111：保留旧残留冷开恢复未连接，没有自动启动；显式启动后出现 VPN 进程并进入运行态，停止后 VPN 进程退出。再次覆盖安装打开仍为未连接。
- 启动后用系统浏览器访问 Google HTTPS 204，在本次 VPN 进程日志中确认一条 `www.google.com:443` TCP 连接命中非 DIRECT 出站；不记录节点名称。
- 以上是运行恢复与基本转发验收，不代表冷启动性能对比、8 小时待机耗电或 24 小时稳定性已达标。
