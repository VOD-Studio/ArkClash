# 0037 VPN 进程被回收后在前台恢复连接

## 状态

已采纳。

## 背景

HBP-AL00（API 26）上，VPN 扩展进程的 `oom_score_adj` 一直是 500，界面在前台时也一样。OpenHarmony memmgr 把 500 定为 `RECLAIM_PRIORITY_NO_BIND_EXTENSION`：扩展进程的回收优先级取绑定它的进程中最好的一个再加 100，没有进程绑定时停在 500。ArkClash 只用 `startVpnExtensionAbility` 启动扩展，不做绑定。界面进程在后台是 300 或 380，普通后台应用是 400，所以整机内存紧张时，VPN 进程会先于普通后台应用被回收。[ADR-0036](0036-vpn-memory-pressure.md) 记录的 `SwapFull`、`LowMemoryKill` 都属于这种情况。

API 26 的长时任务只能由 UIAbility 申请，后台模式里也没有 VPN 类型；`vpnExtension` 没有常驻、始终开启或连接扩展的接口。系统回收扩展后不会重新拉起它，界面进程这时已被冻结，也无法立即发现隧道断了。

## 决定

UI 在前台确认旧宿主已经停止、准备改写 `runtime.json` 时，先读出上一份连接意图（`client/CoreClient.ets` 的 `performStartCore`）。上一份 `vpnIntent` 是 `started`，而当前实例又没有停止回执，说明用户没有断开，扩展也没有正常销毁，宿主只能是被杀或崩溃。新内核就绪后，由发起启动的 `Connection.ensureReady` 恢复一次连接，hilog 记 `vpn_resume_interrupted`。

- 用户断开时界面先写 `stopped`。在系统设置里断开、被其他 VPN 接管，都会走扩展销毁并留下停止回执。这几种情况都不恢复。
- 只在前台、未连接、未在切换时恢复，每次宿主退出只恢复一次。失败时不弹错误，界面保持断开，用户手动连接时照常显示原因。常见的失败是系统里已经有其他 VPN，`VpnConnection.create` 返回 2203002。
- 并发调用 `startCore` 的其他调用方拿到的 `resumeVpn` 一律为 false，避免重复重连。
- 扩展新实例仍把转发意图复位为 `stopped`（[ADR-0017](0017-core-ready-without-vpn.md)），不在后台拉起扩展抢回 VPN。

## 后果

掉线后，用户不必再自己发现断网并手动连接：回到 ArkClash、内核就绪后即自动重连。锁屏和后台期间被回收仍会断网，一直持续到用户回到应用，这一点要等平台提供提升扩展优先级的途径才能改善。重启手机、覆盖安装、在设置里强行停止应用，同样不会留下停止回执，下次打开 ArkClash 也会恢复连接。

## 真机验证

2026-11-26，同一台 HBP-AL00，ARM64 Release 包。为模拟系统回收，临时构建（不提交）让 VPN 进程直接退出，不走清理；应用内的代理命中由临时探针读取连接表得到，只看是否走代理，不输出节点名。

| 场景 | 结果 |
|---|---|
| 已连接时覆盖安装，VPN 与界面进程都被结束，冷启动后不点击 | 首页可操作后 4.1 s 记 `vpn_resume_interrupted`，又过 0.2 s 确认 TUN |
| 已连接时退到后台，只结束 VPN 进程，界面进程 PID 不变，再回到前台 | 自动恢复，从开始恢复到确认 TUN 用时 0.24 s，换了新的 VPN 进程 |
| 恢复后用系统浏览器打开 Google | 3 条 Google 连接全部命中 `DomainSuffix` 规则走代理，随后断开正常 |
| 用户断开后结束 VPN 进程，再回到前台 | 只预热内核，没有恢复标记，没有 TUN |
| 用户断开后覆盖安装并冷启动 | 不恢复 |

验证开始时，系统里残留着另一个 VPN 的对象，ArkClash 连接被 2203002 拒绝；用户在系统设置里断开那个 VPN 后才能连接。另外观察到一次断开返回 `vpn_detach_failed`，转发状态停在 `failed`，当时扩展没有记录 Go 返回的错误；按同样顺序重试两次都没有复现。

恢复在内核就绪之后才开始，不进入首帧路径，也不增加轮询或常驻任务，因此不影响冷启动到可操作和待机耗电，新连接延迟的路径也没有变化。这几项本次没有单独测量。24 小时稳定性方面，系统回收的频率不变，变化在于回收后可以在前台恢复连接。
