# 0016 完整观测事件使用受控的 mihomo 构建期补丁

- 状态：目标决策，待实现与升级回归验证（2026-11-13）

## 背景

上游mihomo v1.19.33没有FlClash封装依赖的新连接与DNS完整记录钩子。轮询活动连接会漏短连接；只包装resolver全局变量也不足：`hub/executor/executor.go` 中的 `dns.ReCreateServer(..., s)` 将原始service交给DNS监听，后续更换DefaultService不改变该引用；缓存命中、实际upstream与发起方也不能靠入口名称推测。

因此此前“DNS只需四个全局包装、缺cached可以接受”的草稿撤回。完整功能不能用静默丢字段或查询窗口来验收。

## 决定

不用FlClash的mihomo fork，维护小型构建期补丁。参照既有gVisor流程：复制固定版本模块到`.toolchain/patched/`，检查来源与补丁hash，用临时modfile replace；禁止修改共享Go模块缓存。补丁不适用就构建失败。

实现按实际缺口增加：

- Tracker新建和字节计数/结束的观察点，支持最近请求与包含短连接的累计；不能用活跃快照反推。
- DNS真实查询结束的观察点，包含缓存命中、实际upstream、initiator、结果和耗时。避免单次逻辑查询在嵌套解析中重复计数。
- 自动代理组选中变化、provider加载终态和拨号循环等事件；先检查上游是否已有可用接口，再加必要钩子。

具体插入函数、锁和对象生命周期必须在实现工单记录并写回归测试，不能把设计中的回调名字当上游已经存在的API。无观察者时快速返回，不能宣称严格“零开销”。回调只复制最小不可变摘要、非阻塞入队，不做磁盘/网络/JSON序列化或调用回核心。

事件topic有订阅才进行展示用采集；队列按条数及字节数限额，有明确丢弃策略和计数。记录只在应用内存，不把用户访问域名/节点信息写hilog。路由事件应保留epoch/version/check的缓存语义，不能以反复联网探测代替失效判断。

## 后果

- 能覆盖短连接与DNS缓存路径；仍须夹具和真机证明，不是文档写完即已具备。
- 每次mihomo升级需复验补丁适用、记录完整性、取消/Close、竞态、转发开销；与依赖升级分开提交。
- 将复查项目加入平台陷阱文档的目标架构章节；当前未实现补丁不得写成现有修复。
