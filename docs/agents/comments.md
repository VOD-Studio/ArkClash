# 代码注释规范

适用于 Go（`core/`）、C++（`entry/src/main/cpp/`）、ArkTS（`entry/src/main/ets/`）、脚本和补丁文件。

## 语言

- 新写的注释用中文。专有名词（TLSDESC、fake-ip、VpnExtensionAbility）保留原文。
- 已有的英文注释保持原样，即使改到了它旁边的代码，也由人工统一翻译。
- 例外：注释描述的代码改了，注释已经不对时，重写成中文。过期的注释比没有更危险。

## 写什么

注释只写代码说不出来的信息：

- **非显然的陷阱**：`// 先取地址再读：共享库模式下直接读全局变量会借用 R27 中转，而 R27 正存着 LR。`
- **平台约束**：`// 鸿蒙限制 VpnConfig.mtu 最大 1500`、`// SELinux 不允许应用对 TUN fd 做 fstat`。
- **跨进程、跨语言的约定**：`// 必须和 core/tun.go 的 tunAddress 一致`、`// libclash.so 导出的 C API（core/lib.go），两边一起改`。
- **魔法值的理由**：`const READY_TIMEOUT_MS = 30000; // 首次启动内核可能要解析上万条规则`。
- **导出符号的契约**：调用方要知道的返回值、所有权、线程要求（`// 返回的字符串由调用方用 ArkClashFree 释放`）。

自检：这句话在讲"代码做了什么"（代码已经说清楚了），还是"为什么这样、有什么坑"（代码说不出来）？只写后一种。

## 不写什么

- **复述签名**：名字已经说清楚的，不再用中文翻译一遍。名字是泛词（`start`、`handle`、`update`）时，补一句它具体做什么。
- **设计论证和历史**：为什么选这个方案、否决了什么，写进 commit body 或 `docs/`。注释只管代码现在做什么、有什么坑。
- **短函数里的分隔标签**：几十行的函数不用 `// --- xxx ---` 分段；几百行的文件可以用分段导航。
- **一个包多份 package 注释**：Go 的 `// Package xxx` 只写在一个文件里。

## 字段注释

判断标准：去掉注释，调用方能不能从字段名和类型推断出正确用法？能就不写，不能就写。需要写的通常是：

- 零值、空串、`undefined` 的含义：`stack: string // 空串 = gvisor`
- 合法取值：`stack: string // 'gvisor' | 'system' | 'mixed'`
- 单位和格式：`timeoutMs`、`// RFC3339`
- 跨进程共享的结构（`RuntimeConfig`、`startOptions`、`CoreOptions`）：写清楚哪边写、哪边读。

一句话说得清的用行尾注释，复杂的写在字段上方。

## 存量

新代码（包括搬移的代码）按本规范写。存量里不合规的注释不专门开提交清理，因为别的原因改到那个文件时，顺手整理和本次修改相关的那几处，跟着所属的逻辑变更一起提交。
